# Budget planner (knapsack)

The owner states what she wants (assets, reel seconds) and her limits. The planner returns the best plan that fits and explains what it dropped. It is both a real feature (scope control for a busy owner on free tiers) and the answer to "realistic classroom/small-business constraints of time, connectivity and cost".

## 1. Inputs

```
wanted:  list of (audience, lang, channel) assets, each with owner priority 1-5 (default 3)
reel_seconds: total seconds of reel wanted (0 = none)
limits:
  time_s     wall-clock the owner is willing to wait (e.g. 180)
  money_inr  spend cap, computed from list prices even when free (shadow price)
  review_s   owner attention budget for approving assets (e.g. 480)
calibration: measured latencies and prices (see section 5)
```

## 2. Costs (per item)

Three resource dimensions, all additive:

| Dimension | What it measures | Source |
|---|---|---|
| `T` rate-limit time (s) | How long the bucket for that call class is occupied | RPM limits: text 10 -> 6 s per call, image 1K 10 -> 6 s, image 2K 5 -> 12 s, 3K/4K 1 -> 60 s, video 1 -> 60 s per call, plus measured generation time |
| `M` money (INR) | List price converted at a configurable rate; free tier makes real spend 0 but the cap is still honoured | Text $0.05/1M in, $0.15/1M out; image $0.010 (1K) to $0.024 (4K); video $0.025/s 720P |
| `R` review effort (s) | Owner time to check and approve | Per type: copy 20 s, poster 30 s, reel 45 s (tunable) |

Classes run in parallel buckets, so wall-clock is not the sum. Estimated time:

```
time_est = max(T_text, T_image, T_video) + overhead
           (overhead = serial steps: brief, facts approval is excluded because it happens before planning;
            validation + scoring tail ~ calibrated)
```

`T_text`, `T_image`, `T_video` are the sums of bucket time per class for the chosen plan.

## 3. Shared (fixed) costs: why this is not a plain knapsack

Copy is generated by **one batched call per language** covering all channels and audiences, and one scoring call covers all personas x variants. So:

- Selecting any asset in a language pays that language's fixed batch cost once, then a small marginal cost per additional asset.
- A reel pays a per-clip cost (video is the dominant term).

This is a multi-dimensional knapsack with fixed charges. Because the language set is at most 3, the solver **enumerates language subsets (<= 8)** and solves a standard multi-dimensional 0/1 knapsack for each; the best feasible result wins. Reel clips are a **multiple-choice** group: pick a clip-length combination whose total meets `reel_seconds` where clips are 4, 8 or 12 s (Agnes video limit is 4-12 s per clip). A 16 s reel is 8+8, 12+4 or 4x4; cost grows with the number of calls (1 RPM) and seconds (money).

## 4. Objective and solving

Value of an item = owner priority (1-5) x coverage weight, where coverage weight rewards covering every (audience, language) pair at least once before doubling up (diminishing returns). Maximize total value subject to:

```
sum(T-per-class) <= time_s      (using the max-over-classes model)
sum(M)           <= money_inr
sum(R)           <= review_s
```

Implementation: build an ILP (binary variable per asset, integer per reel clip choice, binary per language fixed charge) and solve with `scipy.optimize.milp` (free, no extra service) or `ortools` CP-SAT. With <= 40 variables it solves in milliseconds, so the UI recomputes live. A greedy fallback (value per normalized cost) exists for the client-side preview.

Output:
```json
{
  "chosen": {"assets": ["locals-kn-instagram", "..."], "reel_clips": []},
  "dropped": [{"item": "reel 16s", "reason": "video queue needs 330 s; time limit 180 s"}],
  "cost": {"time_s": 115, "money_inr": 2, "review_s": 400,
           "calls": {"text": 14, "image": 2, "video": 0}},
  "binding": ["review_s"],
  "alternatives": [{"label": "9 assets + 2 x 16 s reels", "cost": {...}}]
}
```

`binding` lists which constraint(s) are tight so the UI can say "your review limit is the bottleneck: raise it by 2 min to add 3 assets".

## 5. Calibration

Costs are measured, not guessed. The backend runs calibration ([calibration](calibration.md)) and the planner reads the `calibration` records; per-provider rate limits come from the owner's tier or custom limits ([settings](settings.md)).

1. Quick calibration runs at startup (if enabled), when a key or tier changes, and on demand: text probes, image probes, optional video (full mode only). Record latency and token usage.
2. Latency percentiles and token usage per call type are stored per provider in the `calibration` table.
2a. RPM per class comes from the tier (Agnes Free: text 10, image 1K 10 / 2K 5 / 3K-4K 1, video 1; Enterprise and Token Plan are higher) or the user's custom value, so a user's own key can make video or large plans feasible.
2b. Image generation can take tens of seconds and video has queue + generation time, so latency (not only the 6 s/60 s bucket spacing) enters the time model: `class_time = (n_calls - 1) * (60/RPM) + p50_latency`.
3. The solver uses p50 for the plan and shows p90 as the risk range ("finishes in 1:55, up to 2:30").
4. Cache hits cost 0 time and 0 money; the planner knows which asset prompts are already cached and prefers them.

## 6. Worked examples (illustrative; real numbers come from calibration)

Assumptions: 3 languages, 2 audiences, channels Instagram/WhatsApp/poster; posters use the owner's real photo (no image call) unless a background is requested; review costs copy 20 s, poster 30 s, reel 45 s; limits time 180 s, review 480 s.

| Config | Assets | Reels | Text calls | Image calls | Video calls | Est. time | Review | Fits? |
|---|---|---|---|---|---|---|---|---|
| A | 18 | none | ~14 | 0-2 | 0 | ~1:55 | 6 x 30 + 12 x 20 = 420 s | Yes |
| B | 9 (one audience) | 2 x 16 s | ~9 | 0-1 | 4 (2 reels x 2 clips) | video alone >= 4 x 60 s = 240 s | 9 assets ~200 s + 2 x 45 s | Only if time_s >= ~300 |
| C | 18 + 16 s reel | 1 x 16 s | ~14 | 0-2 | 2 | >= 120 s video + tail | 420 + 45 | Over 180 s: planner offers dropping reel or raising time |

The planner is honest about the dominant cost: video at 1 RPM. It will propose "generate reels in the background after you approve the copy" as an alternative that changes the time model (async), which the UI shows as a separate "background" bar.

## 7. UI contract (S5)

- Toggles for languages, channels, audiences, reel seconds, three sliders for limits.
- `BudgetMeter` three bars with caps; binding constraint highlighted.
- Plan list with each dropped item and the cheapest fix.
- "Alternatives" chips (at most 3) that preload a different plan.
- Server confirms the plan before generation; the confirmed plan is stored in `plan`.

## 8. Edge cases

- Infeasible even with one asset: show the minimum feasible plan and which limit to raise.
- Facts change at runtime: planner re-runs only for assets whose facts changed (cost = blast radius only).
- Cached outputs: shown as "free" items, always included first if wanted.
- Fallback (saved demo output) assets count as 0 cost but are labelled.
- Money is shadow-priced because the free tier makes actual spend 0; the UI shows both "list price" and "you pay Rs 0".

## 9. Tests

- Property test: solution never violates any limit; value is >= greedy value.
- Language-subset test: removing a language reduces fixed cost by exactly its batch call.
- Reel test: 16 s requests return clip combinations summing to 16 with 4-12 s clips, minimum calls first.
- Determinism: same input + calibration -> same plan.
